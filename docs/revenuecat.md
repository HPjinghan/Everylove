# RevenueCat 接入（everylove 口径 + myuki 原手册）

> 动内购、付费墙、webhook、流量 / 语音时长的扣账之前先读本文件（CLAUDE.md §11-7）。上半部分是 everylove 自己怎么套（2026-10-21，D-215）；下半部分是 myuki 的原手册，编号（第 n 条、§n）都指原手册，原样保留。苹果与 RevenueCat 的文档会变，动手前按原手册开头的说法核一遍官方页面。

## E. everylove 怎么套

### E1 · 我们和 myuki 哪里不一样

| | myuki | everylove |
|---|---|---|
| 卖什么 | 只有消耗型（硬币） | **订阅 + 两种消耗型**：Pro / Max 自动续期订阅；流量包（MB）、语音分钟包（订阅用户才能买）——原手册 §10 那半边我们也要做 |
| 余额在哪 | 服务器自己的库 | **现在全在本机**：`store.traffic` / `store.voice` / `store.plan`，随整份快照进 `snapshots`，客户端想改就改。试装可以，真钱不行 |
| 扣账在哪 | 服务器的花费函数 | 客户端 `features/traffic.ts` 在每次调用之后扣；账单归属 user / house / included 也是客户端标的 |
| 后端 | stage + prod 两个 Supabase | 目前一个 Supabase 项目（待开发者确认有没有 stage） |
| 热更 | runtime 跟原生指纹走 | `runtimeVersion.policy = sdkVersion`：**加原生模块不会换 runtime**，热更照样送到没装 RevenueCat 的旧包（见 E3） |
| 主体迁移 | 迁过一次 | 也刚迁过（D-214，Kotoko → BIIBIT）：新 app 一开始就在新主体建商品，没有旧商品 ID 要兼容 |

### E2 · 定下的技术口径（D-215）

1. **内购走 RevenueCat**（`react-native-purchases`），照原手册 §3 的三条路架构：webhook + app 上报交易号 + 定时对账，服务器向 RevenueCat v2 核实才入账。
2. **真钱的余额搬到服务器**：流量余额、语音分钟包、送的 5 分钟通话、订阅档位都以服务器为准，本机 store 只当显示缓存（快照里的这几项不再被信任，恢复时以服务器为准）。
   - 订阅档位：服务器以 webhook / v2 的 entitlement 为准（原手册 §10）；客户端用 `customerInfo.entitlements.active` 只决定显示什么。Pro 每月 6000 MB 的发放从客户端的 `traffic-grant` 任务改为服务器按续订事件发。
   - 扣账挪进代理 `supabase/functions/ai`：上线后正式包只有代理一条路（本地 key 只在 `__DEV__`），代理已经拿到每次调用的 usage，按 `lib/traffic.ts` 同一张换算表在服务器扣。照原手册 §3 末条：锁钱包行是每条花费路径的第一句；先扣（或预扣）再调，失败退回。
   - 账单归属不能再信客户端：客户端可以把什么都标成 house 来白嫖。服务器按调用类型判归属，house 的部分就是现在的「后台保险丝」，从内存挪到服务器的每人每天计数（和 `ai_usage` 同一种原子自增）。
   - 每天免费 100 MB、Free / Pro / Max 每天的语音分钟这类「按天重置」的额度也在服务器算，自然日按服务器时区还是用户时区写进实现时定。
3. **App User ID 用服务器发的随机 UUID**（原手册第 1 条），不用 Supabase user id。匿名会话（只作代理凭证）不连 RevenueCat、不能买：购买前必须真登录（Apple / 邮箱），未登录点购买先进 `app/auth.tsx`。
4. **公开 key 写成代码常量**（原手册第 31 条）：我们的 `scripts/release-update.mjs` 会剥掉 Supabase 以外所有 `EXPO_PUBLIC_*`，放 `.env` 的 key 必然在热更里变空，这条对我们是硬性的；`sk_` 只在 Supabase secrets，脚本的秘密扫描加上 `sk_` 前缀。
5. **原生模块与热更**：`react-native-purchases` 只碰一个文件，`purchases.ts` 里 `require` 包在 try 里，没有原生模块时 `purchasesSupported()` 为假、付费入口换成一行「下个版本开放」——这样带它的 JS 热更到没装原生模块的旧包上不会崩。另外考虑把 `runtimeVersion` 换成 `fingerprint` 策略，免得以后每加一个原生模块都靠人记（换了之后热更只到同指纹的包）。Expo Go 里买不了，真机走 dev client（D-165）。
6. 收费开关在服务器一处判断，先只对测试名单开（原手册 §8.5）；试装的「点即到账」在开关关着时照旧，开关开了就换成真购买，GM 加流量 / 加分钟只留开发构建。
7. 退款扣不够记欠账、余额不为负（原手册第 15 条）；买来的流量与分钟包不过期（App Review 3.1.1，现行口径本来就不过期），每天免费的 100 MB 与订阅额度是送的、可以按天清零。
8. 订阅必须有「恢复购买」（原手册 §10）；消耗型照原手册第 30 条不做恢复按钮，余额跟着账号走。

# myuki 原手册：RevenueCat 接入的流程与踩过的坑

> 给开发者：把这份文件放进你们仓库（比如 `docs/revenuecat.md`），在 CLAUDE.md 里加一行「动内购、付费墙、webhook 之前先读 docs/revenuecat.md」。

写给另一个 app 的 Claude Code。2026-10-21 由 myuki 的 Claude Code 整理，来源是 myuki 仓库里内购的设计文档、四轮代码审计、两次「对照官方文档」的核对和上线记录，只留能搬到别的 app 的部分。

RevenueCat 和苹果的文档会变。凡是写着「文档说」「实测」的，动手之前打开官方页面再核一遍；对不上时以官方现在的说法为准，并告诉开发者这里哪一条过时了。

## 0. 我们的场景

- iOS 先行，卖**消耗型**商品（硬币，七个礼包），余额记在**我们自己的数据库**里。没做订阅，没做 Android。
- 栈：Expo SDK 54（React Native 0.81）、`react-native-purchases` 10.x；后端 Supabase（Postgres 加 Deno 写的 Edge Functions）。
- stage 与 prod 两个后端，共用**一个** RevenueCat 项目。
- 时间线：2026-10-03 设计，10-04 服务端上 stage，10-06 第一次沙盒购买、合入、服务端上 prod，10-09 对所有人开收费，10-19 把 App User ID 换成不公开的随机 id。

你的场景不同时：做订阅或非消耗型的，先读 §10；后端不是 Supabase 的，把「Edge Function」「迁移」换成你们的写法，原则不变。

## 1. 代价最大的八个坑

1. App User ID 用了别人读得到的账号 id：任何人都能读别人的购买、把自己的收据挂到别人名下（第 1 条）。
2. 调了 `logOut()`：之后的购买记在一个匿名 id 上，到不了任何人的账户（第 2 条）。
3. 把 `customerInfo` 里的交易 id 交给服务器：那是 RevenueCat 自己的 id，永远查不到（第 21 条）。
4. RevenueCat v2 API 购买记录里的 `product_id` 是 RevenueCat 自己的 `prod…`，不是 App Store 的商品 ID：服务器核单那条路永远报「不认识的商品」，而测试一直是绿的，因为测试夹具是照自己的想象写的（第 20 条）。
5. TRANSFER 之后，原买家在 RevenueCat 的购买列表是空的：按人读列表的对账会漏掉这些购买的退款（§5 步骤 4）。
6. RevenueCat 后台的恢复行为选了「留在原账号」：同一个 Apple ID 上的第二个账号付了钱却永远记不下来（§6）。
7. 对用户说「购买失败」：其实可能已经扣款（第 23 条）。
8. RevenueCat 的公开 key 放在 `.env` 里打包：哪台机器忘了填，就发出一个买不了东西的包（第 31 条）。

## 2. 开工前先问开发者

这些答案决定架构，写代码之前问清：

1. 卖的是消耗型、非消耗型还是订阅？买到的东西记在哪：自己的库，还是只信 RevenueCat 的 entitlement？
2. 只有 iOS，还是也有 Android？
3. app 的用户 id 是什么，**别人读不读得到**（公开资料页里的 id、用户名、邮箱都算读得到）？
4. 几个后端环境？共用一个 RevenueCat 项目还是分开（§8.4）？
5. 上架哪些市场？（欧盟要先申报 DSA 交易者身份。）
6. 怎么打包，有没有 OTA 热更？
7. 以后要不要按买家实付的钱给别人分成，或者按国家报税？要的话 §9 里有几样东西要在第一笔正式购买之前就开始存。

## 3. 架构

```
                 StoreKit 购买（RevenueCat SDK）
                           │
      ┌────────────────────┼──────────────────────┐
      │                    │                      │
 ① RevenueCat webhook   ② app 把苹果交易号      ③ 定时对账
    （先验签）             交给服务器              （每 10 分钟，补上
                          （服务器去 RevenueCat     webhook 丢掉的退款）
                           v2 API 核实，不信 app）
      │                    │                      │
      └────────────────────┴───────────┬──────────┘
                                       ▼
                 同一组数据库函数：入账 / 退款 / 撤销退款
                 按（商店，交易号）唯一：谁先到谁入账，
                 后到的什么都不改
```

- **余额只在自己的库里。** 消耗型的兑换 RevenueCat 本来就不管（官方文档：要在 RevenueCat 之外处理）。我们没用 RevenueCat 的 Virtual Currency：它自己记一本账，余额不能为负、退款最多扣到 0，官方 FAQ 说它和自己的账并存时两边会对不上；而且每次扣费都会变成一次外部请求。
- **客户端不决定任何钱。** 一个商品值多少，只写在服务器的商品表里；app 只交苹果的交易号，服务器向 RevenueCat 核实之后才入账。商品 ID 里的数字永远不拿来算钱。
- **三条路，任何一条都能入账。** 所以 app 不必「一定要成功」，只需要对用户说实话（第 21–27 条）。SDK 在 RevenueCat 记下交易之后就把交易标成完成，早于我们入账；这可以接受，因为交易已经记在 RevenueCat 的服务器上，三条路都去那里拿。
- **一笔交易一行，行说「现在是什么」，钱包跟着行走。** 交易行记着：值多少（第一次见到时按商品表定下，之后改价不影响）、属于哪个账号（第一次见到时定下，永不改）、现在是否已退款。一个 converge 函数让钱包与行一致、只动差额；每一次变动有自己的流水幂等键：首次入账 `iap:<商店>:<交易号>`，第 n 次退款扣回 `…:refund:<n>`，第 n 次撤销退款 `…:reinstate:<n>`。
- **沙盒照样入账，营收只算正式环境。** TestFlight 和苹果审核买的都是沙盒，而审核连的是 prod 后端，不入账审核就过不了。交易行记 `environment`，营收指标只数 `production`。代价是 TestFlight 测试者在 prod 上买东西不花钱；测试者是邀请制，我们接受了。
- **如果你们也自己记余额**（硬币、点数、额度）：锁钱包行（`select … for update`）是每一条花费路径的第一句，它同时挡住并发抢余额、同一下双击、免费额度并发超发；先扣费再干活，失败退款（「先检查、再干活、最后扣费」会被并发白嫖：50 个并发全过检查、只有 1 个付钱）；异步任务的退款挂在任务行的触发器上，因为「每个失败出口都记得退」靠人记不住；钱的表不加指向账号的外键（删号的级联会把流水和归属一起抹掉），交易与流水在删号后保留，作为退款与税务凭证。

## 4. 规矩

每条一句规矩，后面是为什么。编号全文通用。

### 4.1 身份（App User ID）

1. **App User ID 用服务器给每个账号发的随机 UUID，不用账号 id。** RevenueCat 的公开 key 就在包里，知道一个 App User ID 就能以那个人的身份调 RevenueCat：读他买过什么、什么时候买的，把自己的收据挂到他名下。RevenueCat 的文档也要求 id 不可猜。我们一开始用的是 Supabase 用户 id，它匿名可读，审计时才发现，上线前补了一次迁移，还要兼容已经用旧 id 买过东西的测试包。**一开始就用随机 UUID。** 做法：一张只有服务器读写的表（账号 → UUID），第一次问时发、永不改；app 经一个只回答本人的接口拿到它，答案里带上账号 id 让 app 核对是给谁的；在手机上存一份（断网也能用同一个 id 启动）；三处都拿不到就**先不连 RevenueCat**，永远不退回账号 id。UUID 还有个好处：SDK 会自动把它设成 StoreKit 的 `appAccountToken`，苹果签名的交易记录里也能对上是谁。（已经用账号 id 上线过、要换的，找 Patrick 要 myuki 当时的换法。）
2. **换人只调 `logIn(新 id)`，永远不调 `logOut()`。** `logOut` 会生成一个匿名用户，之后的购买记不到任何人。签出时只把购买按钮藏起来，SDK 里留着上一个人的 id 没关系，下一个人登录时 `logIn` 换掉。用单测守住：全库搜不到 `logOut(`。
3. **身份变更排成一个串行队列。** 签入和签出同时发生时，不排队的话 SDK 可能停在另一个人身上。
4. **购买按钮只在 SDK 确认在当前这个人身上之后才可点；点下去之后、打开苹果面板之前，再核一次 `getAppUserID()`**，对不上就不打开。买到的东西落在 SDK 当时登录的那个人身上，不是屏幕上显示的那个人。
5. **有登录态就在启动时 configure。** 苹果要求 app 一启动就监听交易：关着 app 时家长批准（Ask to Buy）的购买、上次丢了回话的那一笔，都在这时交上来。JS 重载（热更新被应用）之后原生 SDK 仍是配置好的：先问 `Purchases.isConfigured()`，没配置才 `configure`，配置了但 id 不对就 `logIn`。

### 4.2 webhook

6. **先验签，再读任何字段。** 签名头是 `X-RevenueCat-Webhook-Signature: t=<unix 秒>,v1=<hex>`，HMAC-SHA256 签的是 `"<t>.<原始 body 字节>"`，密钥按原始字节。比较用平台自带的常数时间 verify（Web Crypto 的 `crypto.subtle.verify`），不要自己比字符串。签名对了再看时间：t 与现在差 5 分钟以上就拒（RevenueCat 每次重试都重新签名，所以这只拦重放）。没配签名密钥的环境一律拒收（我们回 503：RevenueCat 的重试会持续约两个半小时，期间配上就不丢）。集成如果另设了固定的 Authorization 值，两样都要对。
7. **先写下，再处理；处理失败也回 200，由自己重试。** 验签之后，事件先进收件箱表（主键是 RevenueCat 的事件 id），然后在一个短事务里处理。处理出错、或者买的是没登记的商品，就记成 failed 留在表里，由自己的定时任务从 5 分钟起翻倍、最长 12 小时重试，**永不放弃**。只有数据库根本没写进去时才回非 200，让 RevenueCat 重送。原因：RevenueCat 只认 200，非 200 时它在 5、10、20、40、80 分钟后各重试一次，五次之后就不管了；它的超时是 60 秒。
8. **webhook 接口不要求登录。** RevenueCat 不带你的用户 token，签名就是唯一的钥匙。（Supabase：在 `supabase/config.toml` 里给这个函数写 `verify_jwt = false`，不要只靠部署命令加 `--no-verify-jwt`，换一种部署方式它就又要 JWT 了。）
9. **签名密钥只在创建或轮换时显示一次，轮换会让旧密钥立刻失效。** 所以环境变量支持逗号分隔放几把：轮换之后马上换上新的，期间失败的投递靠 RevenueCat 的重试补回；要一秒都不断，就另建一个指向同一地址的集成，两把并存，再删旧的。测试环境可以多放一把只给 e2e 用的测试值；**prod 永远不放测试值**。
10. **只有三种事件动钱（消耗型）：** `NON_RENEWING_PURCHASE` 入账；`CANCELLATION` 对一次性购买就是退款（价格是负的）；`REFUND_REVERSED` 撤销退款（只有 App Store 有）。不动钱的：`TEST`（记成 ignored）、`TRANSFER`（币不跟着走，第 14 条）、别的商店、`PROMOTIONAL`（RevenueCat 后台送的，不是买的），以及你库里找不到的人。
11. **找人要查全：** 依次查 `app_user_id`、`original_app_user_id`、`aliases`（RevenueCat 文档要求都查）。

### 4.3 入账、退款与顺序

12. **至少投递一次、不保证顺序，照这个写：**
    - 同一事件重送：收件箱按事件 id 认出来，原样答复，什么都不改。
    - 不同事件说同一笔交易，或者 webhook 和 app 的上报同时到：交易行按（商店，交易号）唯一，只入一次。我们用六路 webhook 加四路 app 上报同时打验过。
    - 退款比购买先到：先记下「已退款」，购买到的时候不入账。
    - 退款撤销：只认 `event_timestamp_ms` 比它撤销的那次退款新的，旧的忽略；对从没见过的购买，撤销就等于购买成立，照常入账。
    - 从 API 读到的状态是「观察」，不是「事件」：它能补一笔没入账的购买、能扣回一笔已退款的购买，但不推进先后顺序，永远不撤销一次已经宣布的退款撤销，也永远不自己把退款撤销（只有带时间的事件能）。
13. **锁的顺序固定：收件箱行 → 交易行 → 钱包。** 所有路径同一个方向，才不会死锁。
14. **币永远留在购买时的账号。** `TRANSFER`（同一个 Apple ID 被另一个账号拿来买或恢复）不搬币，之后的退款也从原账号扣：退款按交易行找账号，不管事件报的是谁、是从谁的列表里读到的。
15. **退款扣不够就记欠账，余额永不为负。** 先从买的那部分扣回，不够的记在钱包的 `debt` 列上，下一次买币先还欠账；送的币不动。每次退款都在 app 里告诉本人扣了多少、还欠多少：苹果的退款处理文档要求对退款采取的动作要在 app 里说明。（这样现有的扣费函数一个都不用改，它们只看余额。）
16. **买来的虚拟货币不能过期**（App Review 3.1.1）。送的可以过期，要分开记。
17. **一个商品值多少只看服务器的商品表；服务器不认识的商品，app 不显示。** app 把 RevenueCat 当前 offering 里的包和服务器的商品表取交集再显示：不在表里的商品，付了钱也入不了账。webhook 遇到不认识的商品：记 failed、立刻报警（有人付了钱还没拿到东西）；往表里补上那一行，事件自己重试入账。下架的商品照样给已经买过的人入账。
18. **商品 ID 一旦被 App Store Connect 收下，就不能改名、也不能再用。** 我们的 ID 里写了币数（`….coins.100`），后来整个价格体系乘了 10，ID 里的数字就和实际入账对不上了，只能将错就错（服务器表里写真实的数，代码永远不解析 ID）；后来换开发者主体建新 app，新 app 的商品也不能沿用旧的 ID，因为两个 app 的购买按同一张服务器商品表入账，同一个 ID 只能对应一个数。建议：ID 里要么不写数量，要么写的就是入账数，并且接受它以后不会再变。App Store Connect 里商品的显示名改了要重新送审，改之前苹果的购买面板上显示的仍是旧名字。
19. **每个字段都防一手。** 购买数量设上限（我们是 1 到 10）；数字是字符串、数量离谱这类格式错乱一律当作缺失，不要让一条事件因为一个字段永远失败。
20. **外部 API 的同名字段不等于同一个值；测试夹具照官方文档的例子写，不照自己以为的写。** v2 API 购买记录里的 `product_id` 是 RevenueCat 自己的商品 id（`prod…`），webhook 里同名的 `product_id` 才是 App Store 的商品 ID。我们的服务器按 App Store ID 查商品表，于是 app 上报那条路永远答「不认识的商品」，只剩 webhook 一条路在入账；夹具里写的是 App Store ID，所以测试一直是绿的，打包前的审计才发现。修法：读 `GET /v2/projects/{project_id}/products`，建一张 `id → store_identifier` 的映射缓存起来（§5 步骤 3）。

### 4.4 客户端的一次购买

21. **交给服务器的是购买结果里的 `transaction.transactionIdentifier`**（苹果的交易号）。`customerInfo.nonSubscriptionTransactions[].transactionIdentifier` 是 RevenueCat 自己的 id，拿它去查永远查不到，服务器会一直答「还没记下」。
22. **交易号先写进手机，再问服务器。** 按账号分开存，七天后丢弃，最多留 20 笔；问不到的，下次启动或回到前台再交。
23. **永远不说「购买失败」，除非错误码确定发生在付款之前。** 只有取消、等待家长批准、这台手机关掉了购买、商品不卖、配置错误、商品请求超时这一类算付款之前。其余所有错误都可能已经扣款，要说「购买没有完成。如果已经付款，会自动到账，到账时会通知你」。
24. **每一次网络请求的时限要短于包住它的那个等待。** 我们问服务器「确认这一笔」最多问一分钟，而我们给所有函数调用设的通用时限是 160 秒：一条挂住的连接会等满 160 秒，苹果面板关掉之后礼包那一行就一直转圈。现在每次问有自己的 20 秒时限（全量读 35 秒）；一分钟之内，服务器答 202 就按它说的间隔（3 秒）再问，没回话就按 1、2、4、8 秒退避；一分钟还没确认，就说「还在确认中，到账时会通知你」，之后 15 秒、30 秒、1 分钟、2 分钟各追问一次（换了账号就停）。
25. **好几条路都可能交同一笔：正在问的交易号记在一处，宣布之前先确认还没被别的路交掉。** 购买本身、之后的追问、启动时的补交、全量读，可能同时拿着同一笔；只问一次，只说一次「已到账」。同一时间只允许一笔购买，所有屏共用这个「购买中」的状态。
26. **记账用的读取永远不挡用户正在等的那一下。** 比如为了判断「有没有新购买」去读 RevenueCat 的购买数，最多等 2 秒，而且不挡苹果面板、不挡「已到账」；设一个统计属性最多等 1 秒。弱网又没有缓存时，SDK 会一直等到它自己的网络超时。
27. **启动与回到前台：先交手机上留着的交易号，再「有理由才」全量读。** 理由只有两个：RevenueCat 记着的一次性购买数比这台手机上次看到的多（至多每 30 秒一次），或者过去 24 小时里在这台手机上开始过购买（至多每 10 分钟一次）。在付款之前就结束的（取消、关掉了购买、连不上 App Store）不留这个 24 小时的标记，否则白白触发一整天的全量读。买完就不再动的人不花任何读取。
28. **价格只用 StoreKit 给的本地价格字符串**（`product.priceString`），永不写死，其他地区的价格由苹果按档位换算。
29. **钱包页每次进屏都读最新的。** 退款是服务器对账时扣回的，客户端没有任何动作能让缓存失效，缓存的余额会撒谎。
30. **消耗型不做「恢复购买」按钮。** App Review 3.1.1 只要求可恢复的内购提供恢复；币在服务器上跟着账号走，换手机登录就在。订阅和非消耗型**必须**有，见 §10。

### 4.5 打包、key 与配置

31. **公开 key（`appl_` 开头）写成代码常量，按打包时的 bundle ID 选；不放 `.env` 或构建变量。** 我们的 OTA 热更是用每台开发机自己的 `.env` 打包的，哪台忘了填就会发出一个买不了东西的包。secret key（`sk_` 开头，给 v2 API 用）只放在服务器。用单测守住：只有一个文件 import SDK；key 只能是空或 `appl_` 开头；app 代码里没有 `sk_`。
32. **RevenueCat 是原生模块：要出新的原生包，Expo Go 里买不了。** 开发用 dev client。网页预览给一个影子文件（我们是 `purchases.web.ts`）导出同样的接口、全部回答「不支持」。没有原生模块或没有 key 时让 `purchasesSupported()` 为假，付费入口换成一行「下个版本开放」，免费的出路照常显示。
33. **（有 OTA 热更时）加原生模块会改原生指纹，之后的 OTA 送不到旧包。** 任何要发给旧包的东西（比如「最低版本」强制更新闸），必须在合入 RevenueCat 之前用 OTA 发出去。我们最后决定不发那次 OTA、直接出新包，代价是旧包上没有那道闸，只能在 App Store Connect 里让那几个旧 TestFlight 包过期。
34. **换开发者主体（比如从一家公司换到另一家）就是一个新 app。** 商品要在新 app 里重建（ID 见第 18 条）；RevenueCat 在同一个项目里加第二个 App Store app，offering 的每个 package 各挂两个 app 的商品；公开 key 按 bundle ID 各一把；开发包也要在新团队重新打，旧团队的开发包装上新代码会拿到别的 app 的 key，买不了。顺带：Sign in with Apple 的用户 id 按团队分，老用户在新 app 里登录会进一个新账号，要另做账号迁移。

## 5. 接入顺序

每一步都有验收，过了再走下一步。

**步骤 1：服务器的表和入账函数（先不接 RevenueCat）。**
- 表：商品表（商品 ID → 入账数、是否在卖；所有人可读）；交易表（主键：商店 + 交易号；只有服务器读写）；收件箱（主键：RevenueCat 事件 id；状态 pending / done / ignored / failed、尝试次数、下次重试时间；只存你代码读的字段）；每人一行的读取记录（给限流和对账用）；钱包上的欠账列；App User ID 表（账号 → 随机 UUID）。
- 函数：入账、退款、撤销退款三个，都经同一个 converge；收件箱的重试定时任务。**写重试函数的同一个迁移里就把定时任务排上**，推完查一眼它真的在定时任务表里（我们有过写了函数、注释说是定时任务、却从没排上的事）。
- 验收：e2e 用自己签名的模拟事件跑完 §7.1 那张表。

**步骤 2：webhook 函数**（验签 → 收件箱 → 处理），配好签名密钥。
- 验收：在 RevenueCat 后台发一条测试事件，回 200，收件箱记成 ignored（test）；用编造的密钥签的事件回 401。

**步骤 3：app 上报接口**（我们叫 `iap-sync`，要登录）。
- 收到交易号：向 RevenueCat 查 `GET /v2/projects/{project_id}/purchases?store_purchase_identifier=<交易号>`。只认 `customer_id` 是调用者的，或者 `original_customer_id` 是调用者的（转移过的购买；注意它指的是这串购买历史里最早的那个账号，§5 步骤 4）。查到 `owned` 就入账，`refunded` 就记成已退款；RevenueCat 还没记下这笔（少见的竞态）回 202「稍后再问」；拿别人的交易号来问回 403。
- 不带交易号：读这个人的全部购买 `GET /v2/projects/{project_id}/customers/{customer_id}/purchases`（分页，每页最多 100，用 `starting_after`），同一个人每分钟至多一次。用来补丢在半路的购买、家长后来才批准的购买。
- **商品 id 要映射**（第 20 条）：读 `GET /v2/projects/{project_id}/products`（分页），按 `id → store_identifier` 缓存，碰到没见过的 id 至多每分钟重读一次。读不到（密钥缺权限、RevenueCat 出错）时：账上已经有这笔就照实答，没有就回 202，webhook 照样会入账；日志里写一行原因。
- 限流：每人每 10 分钟 30 次，超了回 429 带等待时间。RevenueCat 的限流按密钥计（2026-10 的文档：客户信息类每分钟 480 次，商品类另有每分钟 60 次），app 这条路和对账共用同一把密钥。
- **2xx 不等于有答案**：正文读不全、不是 JSON、该有列表却是空的，都算失败，下次再问；「没有」只能来自一个读完了的答案。实测：查不存在的交易号回 200 和空列表；查不存在的客户回 404（`resource_missing`）。我们另把 423 当作可重试（按「这个客户正在被改，比如转移中」处理），429 与 5xx 也重试，等待时间按 `Retry-After` 头或错误体里的 `backoff_ms`。
- 验收：拿一个编出来的交易号调，回 202（如果回 503，说明你把 404 或空列表的判断写错了）。

**步骤 4：对账定时任务。**
- 每 10 分钟读一批人：最近 120 天内有仍然有效的购买、7 天没读过的，按「最久没核对」排在前面（不要用 `nulls first` 之类让新来的永远排前面的排序，老的会饿死）。写之前先算清一天能读多少人（我们每轮 60 人，一天 8,640 人）。苹果的退款大多发生在购买后 90 天内。
- **TRANSFER 之后，按人读列表会漏。** 沙盒实测：同一个 Apple ID 换了账号买之后，这个 Apple ID 的全部购买都列在接收方名下，原买家的列表是空的；两笔的 `original_customer_id` 都是最早那个账号，**不是「这一笔的原买家」**。所以对账读一个人时，还要拿他账上仍然有效、却不在列表里的交易，按交易号逐笔查（我们查最新 30 笔）；有一笔没问到，这个人就不标记已读，下一轮再问。
- 验收：报警盯「该读而超期没读的人」，不盯 5xx 的次数（§8.1）。

**步骤 5：客户端。** 照 §4.1 与 §4.4 写。文件这样分比较好测：唯一碰 SDK 的 `purchases.ts`；全是纯函数的规则文件（错误码分类、服务器答复的读法、退避节奏、什么时候全量读）；整条购买路一个文件；根布局挂一个生命周期 hook（启动、回到前台、`Purchases.addCustomerInfoUpdateListener`）。
- 验收：§7.2 的单测守卫全绿。

**步骤 6：第一次沙盒购买必须恰好入账一次**（§7.3）。两条路都说「新入账」，说明两条路拿到的交易号不一样：**停下来查，不要上线。**

**步骤 7：TRANSFER 测试**（§7.3）。

**步骤 8：上线**（§8.5）。

### App Store Connect

- [ ] 签「付费 App 协议」，填完税务和银行信息。没签完之前 StoreKit 取不到商品。
- [ ] 建商品，类型选对（消耗型、非消耗型、订阅），每个都要审核截图：截图规格表里任意一种尺寸都收（我们用的是 1320×2868）。第一个内购项目要和一个新版本一起送审。

## 7. 测试

### 7.1 不花钱的：e2e

用自己签名的模拟事件打真实的测试环境。我们的套件最后是 13 格，下面每一类都逮到过、或者防住过问题：

- 签名：不带签名、签名错、body 被改过、t 超过 5 分钟，都回 401，什么都不读、什么都不写。
- 并发：同一笔购买六路 webhook 加四路 app 上报同时打，只入一次。
- 退款：扣回；钱不够记欠账；下次买币先还欠账。
- 顺序：退款先到、购买后到；退款撤销；比退款还旧的撤销被忽略。
- 别人：拿别人的交易号来上报回 403；别的商店、别人的事件不动钱。
- 不认识的商品：事件 failed，补上商品之后重试入账。
- 重复投递一个大额包：只入一次。
- TRANSFER 之后：读到的退款不管经哪个账号的列表到达，都从买家扣回、通知买家；第二次读不再扣。
- 身份：同一个账号每次拿到同一个 UUID，同时到的几次「第一次」只发一个；客户端读不到 UUID 表；挂在别的 id 上的正式购买不入账。

夹具照官方文档的例子写（第 20 条）。跑完要能证明测试环境零残留。

### 7.2 单测守卫

- 只有一个文件 import `react-native-purchases`；全库没有 `logOut(`；网页影子文件导出的名字和原文件一样；key 只能是空或 `appl_` 开头；app 源码里没有 `sk_`。
- 纯函数：错误码分类、服务器答复的读法、退避节奏（用假时钟）、什么时候全量读、商品 id 映射。
- e2e 分不出读的是哪个 id 的地方（测试环境的 RevenueCat 里没有测试账号的客户，哪个 id 都回 404），就写读源码的单测把接线钉住。
- 每加一个守卫，都把代码故意改坏一次，确认它真的会变红。

### 7.3 沙盒真机：必验的几件

1. **用真的沙盒 Apple 账号，不用 Xcode 的 StoreKit 配置文件。** 用配置文件时 webhook 收到的交易号是 `StoreKitTest_Transaction_…`，和 SDK 给的对不上。
2. **第一次购买恰好入账一次**：一条路答「新入账」，另一条答「已经入过」。两条都答「新入账」就是两条路的交易号不一致，停。顺便核：v2 里这笔的 `status` 是 `owned`，`customer_id` 是你发的 UUID，`store_purchase_identifier` 等于 webhook 的 `transaction_id`，`product_id` 是 `prod…`（证明第 20 条的映射确实需要），日志里没有映射失败。
3. **TRANSFER**：同一个沙盒 Apple ID 先用账号 A 买、再用账号 B 买。应该来一条 TRANSFER（不动钱），两笔各自恰好入账一次，币留在各自买的那个账号。
4. 拿编出来的交易号调上报接口，回 202。
5. 写一个**只读的核对脚本**：列出最近 N 小时的交易行、收件箱、流水、RevenueCat v2 的记录和买家的钱包，逐笔判「恰好入账一次」，退款、撤销、欠账各自列出。上线那天对 prod 再跑一次。

参考数字：webhook 一般在付款后 3 到 7 秒到达（我们四次实测：6.6、3.6、3.4、4.4 秒），通常比 app 的上报早一两秒。

### 7.4 我们没测成的

沙盒退款：苹果只允许从 app 里发起退款请求，要加开发版的按钮、改原生配置、再打一个包，我们跳过了，退款逻辑只靠 e2e 的签名模拟事件。真实环境里没验证到的只剩「苹果的服务器通知是否指向了 RevenueCat」，所以 §6 那一项一定要人眼核一次。

## 8. 上线与运维

### 8.1 报警盯结果，不盯状态码

- 事件处理失败超过 1 小时：红。
- 出现不认识的商品：立刻红（有人付了钱还没拿到东西）。
- 该对账而超期没读的买家（从没读过、而第一笔有效购买已过一天，或者上次读已过 8 天）：有一个就红。我们原来以为「对账接口 5xx 了，定时任务的失败率报警会看见」，复审发现一个十分钟一次的任务在报警窗口里最多失败两次，永远到不了门槛。报警要盯「该做的事没做成」。

### 8.2 排查

- 失败的事件：修好原因之后，把它的「下次重试时间」改成现在，等重试任务捡起来（或者手动调一次重试函数）。
- 不认识的商品：往商品表补一行，事件自己会入账。
- RevenueCat 后台可以手动重送失败的投递。

### 8.3 删号

- 账号确认删除之后，调 RevenueCat 删客户：`DELETE /v2/projects/{project_id}/customers/{customer_id}`，200 是已排队删除，404 是本来就没有，两种都算完成；失败就记下来，下次再试。
- 代价：RevenueCat 对没有购买记录的人收到的苹果通知会忽略，所以删号之后发生的退款，你多半收不到；一次 TRANSFER 之后，删掉接收方还会把另一个账号的购买记录一起从 RevenueCat 抹掉。要追这些退款，见 §9 的苹果通知历史。
- 交易与流水在你自己的库里保留（退款与税务凭证），隐私政策里写明。

### 8.4 stage 与 prod 共用一个 RevenueCat 项目的后果

- 两个环境会收到同一批沙盒事件，各自只认自己库里的人，找不到的记 ignored。
- 同一个沙盒 Apple ID 先在 stage 的包上买、再在 prod 的包上买，会触发 TRANSFER，之后 prod 的全量读会把 stage 那几笔沙盒购买记进 prod 的账号。只有沙盒会这样，不是真钱，我们接受了。
- 密钥按项目授权：给两个环境各发一把 key 也隔不开两边的客户。要真隔开只能分两个项目；那样苹果的服务器通知怎么分，要你自己查文档。

### 8.5 上线顺序

- 服务端先上（表、函数、secrets），客户端后到。客户端先到时要能安全降级：比如拿不到 UUID 就不连 RevenueCat，买东西那一行等着。
- 收费开关放在服务器一处判断（我们是一个返回 true / false 的 SQL 函数，外加一张测试名单），先只对测试名单开；在 prod 上做一次沙盒购买、核过恰好入账一次，再对所有人开。
- 苹果审核员用沙盒在 prod 上买，所以 prod 的 webhook 集成必须发沙盒事件，prod 也必须给沙盒购买入账。

## 9. 进阶：要按真钱分账或按国家报税时

不需要就跳过。需要的话，这些要在第一笔正式购买之前上线，否则早期的购买会缺数据。

- RevenueCat 的 `country_code` 不是店面：它是按买家最后一次请求的 IP 推出来的（开 VPN、出门旅行、跨区的 Apple ID 都会不一样）。店面要从苹果签名的交易记录里读：App Store Server API 的 Get Transaction Info，`storefront` 字段，用 In-App Purchase 密钥调。
- RevenueCat 报的美元价，在美国以外是那个店面含增值税的价格按当天汇率换出来的；算折扣比例要用苹果记录里的当地货币价格。
- 优惠码兑换的、价格为 0 的正式购买不是真钱；苹果说是沙盒、RevenueCat 说是正式的，也不算真钱。
- 删号以后的退款：每天用苹果的 Get Notification History 拉一遍 REFUND 与 REFUND_REVERSED（每个 app、每个环境各一份）。它和 RevenueCat 的事件排在同一个先后顺序里，却是两种时钟（RevenueCat 的 `event_timestamp_ms` 比苹果的签名时间晚几秒），所以历史里的通知等满一天再用，让 RevenueCat 的那一份先落地。
- 同一个 Apple ID 上的两个账号（来过 TRANSFER）可以成对记下来当风险信号。只按服务器发的 UUID 记：账号 id 谁都读得到，按它记下的关联可能是别人拿自己的收据造出来的。沙盒的 TRANSFER 不记（测试者共用测试账号）。

## 10. 做订阅或非消耗型时哪些不一样

我们没做过，下面是要你自己去官方文档核实的点，不是我们验证过的结论。

- 恢复购买必须提供（App Review 3.1.1：可恢复的内购要有恢复机制）。恢复会触发 RevenueCat 的恢复行为（§6），想清楚同一个 Apple ID 在两个账号之间该怎么处理。
- 权益通常以 RevenueCat 的 entitlement 为准：客户端用 `customerInfo.entitlements.active` 决定显示什么；服务器上要按权益放行的接口，仍以 webhook 或 v2 API 为准，不信客户端说的。
- 事件类型多得多（首次购买、续订、过期、扣款问题、换档位等）。**订阅里的 `CANCELLATION` 通常指关掉了自动续订，不是退款**，要看 `cancel_reason` 区分：去读 RevenueCat 文档的 event-types-and-fields 原文。
- 家人共享与 `REVOKE` 只适用于非消耗型与订阅。
- 能直接搬过去的：§4.1 身份、§4.2 webhook、第 12–14 条的去重与乱序、第 21–27 条的客户端写法、§6 的后台设置、§7 的测试方法。

## 11. 可选：把购买报给 GA4 / Google Ads

- 购买事件让 RevenueCat 从服务端发：RevenueCat › Integrations › Firebase，填 Firebase App ID 和一把 GA4 Measurement Protocol API secret（这把 secret 只放 RevenueCat 后台，不进仓库）。价格按商店实际收的，下一次启动才到账的购买也只记一次。app 里不自己记购买：RevenueCat 用 StoreKit 2 并自己完成消耗型交易，Firebase 的自动采集不一定看得到。
- app 只做一件事：`Purchases.setFirebaseAppInstanceID(id)`，用户不让统计时设成 `null`。这个属性是按 RevenueCat 的客户存的，不是按手机：同一个账号的另一部手机可能写进了它自己的 id，所以每次购买之前再写一次这部手机的答案（最多等 1 秒，不挡购买）。
- 集成里关掉沙盒事件。Google Ads 里只导入 `purchase`，不要同时导入 GA4 自动的 `in_app_purchase`，否则会算两次。
- RevenueCat 发出的事件可能带 `user_id`（就是 App User ID），隐私政策和 App 隐私问卷要写明。
